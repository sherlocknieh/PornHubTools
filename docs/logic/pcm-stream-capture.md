# 流式 PCM 捕获（思畅朗读）

## 为什么抓不到音频

思畅的「朗读」不走 `<audio src=...>`：它 `fetch('/api/tts')` 拿一条 PCM16 流，用 `ReadableStream` 边读边转 `AudioBuffer`，交给 Web Audio 播放。页面上没有可下载的媒体 URL，`<audio>` 元素和 `speechSynthesis` 也都没有记录。

所以捕获点只能放在 **网络响应**：拦截 `window.fetch`，在页面消费原响应之前克隆一份。

## 做法

1. 包装 `window.fetch`，只对 `/api/tts` 的响应生效；其余请求原样返回，不改变页面行为。
2. `response.clone()` 拿到 tee 出来的第二条分支，页面继续读原分支，互不阻塞。
3. 读克隆分支累积 PCM16 字节；结束时补齐为偶数长度，加 44 字节 WAV 头（PCM、单声道、16 bit、采样率取 `X-Sample-Rate`）。
4. 生成 blob URL 交给面板，播放用 `new Audio(url)`，下载用带 `download` 属性的 `<a>`。

## 必须注意

- **克隆分支必须持续读**：tee 的未读分支会在内存里排队。超过单条上限时仍然把流读完，只是丢弃数据，不能直接 `return`。
- **流可能被取消**：页面点停止会 abort 原响应，克隆读会抛错；这不是异常情况，已读到的部分要照常落盘。
- **不要用轮询或 DOM 监听**：按钮的实现细节（图标、文案、React 状态）会变，接口才是稳定契约。
- 采样率以响应头为准，写死常量只作为兜底。
- 面板条目在响应到达时就插入（「捕获中」），流结束才生成 blob URL；这样用户点下朗读的瞬间就能看到反馈，长文本也不会以为没生效。
- 捕获阶段没有总长度，进度条只能做不确定动画；播放阶段有了 `audio.duration`，才切成可点击跳转的真实进度。
